# RWKV7 benchmark experiments — RTX 3060 (sm_86)

这份文件是本机的基准/实验结果与分析记录（旧 `script/benchmark_rwkv7.md` 报告与
`docs/benchmarks/` 已移除/并入本目录；MX450 特调记录也已移除，细节见 git 历史）。
正确性验证由测试套件负责：`RWKV_CHECKPOINT_PATH=... .venv/bin/python -m pytest test/`。

## 当前基线（2026-08-08，neo-kernel 分支）

本节是**当前分支可复现的 3060 基线**。后续任何新方案（手写 GEMV、chunk 并行 prefill、
CMIX 融合接入 prefill、量化等）都应在此基线上做新旧对比。

> 注：本节的 tl-fp16 数字采集于旧路径（`demo._rwkv7_base` + 逐 op kernel，commit
> 5d4da6b 时代）。commit a8e2ef7 启用 neo kernels（`RWKV7TL` + `tmix_decode`/
> `cmix_decode`/`cmix_prefill`）后数据见下节「neo kernels 基线（a8e2ef7）」。

### 环境与方法

- GPU: RTX 3060 (sm_86, 12GB)，本机。模型: rwkv7-g1d-0.1b (C=768, H=12, L=12)。
- 命令: `script/benchmark_rwkv7.py --project-checkpoint ...0.1b.pth --device cuda
  --targets faster3a_2607,tl-fp16,tl-bf16,pure-torch --cases 1x1,1x8,1x32,1x64,1x128,8x8,16x16
  --warmup 10 --iters 20 --correctness-check`（正确性门控全过）。
- 所有项目 target（`tl-fp16`/`tl-bf16`/`pure-torch`）默认走
  `make_rwkv7(use_graph=True)` 的 `CUDAGraph` 包装：decode（T=1）+ per-T prefill graph，
  `prefill_graph_max_t=1024`（分支已从旧默认 64 提到 1024）。faster3a_2607 无 graph。
- 注意：`pure-torch` 1x1 单独跑 3.74ms；与 faster3a_2607 同进程混跑时被其 CUDA 扩展
  残留污染到 ~11ms，故表格 1x1 用单独跑的值。其余 case 混跑/单跑一致。

### 结论

- **tl-fp16 仍全面领先**（除 16x16 真 batch 外），T=1..128 快 faster3a 1.8-2.5x。
- **tl-bf16 不再显著慢于 tl-fp16**（旧记录 4x 差距消失）：分支的
  `fused_rank_gemv`/`fused_gates` 融合 + `CUDAGraph` 全覆盖让 bf16 decode 追平 fp16。
  "bf16 在 sm_86 上更慢"的旧结论**已失效**。
- **大 T prefill 的 launch 瓶颈已被 graph 基本消除**：T=256（16x16）tl-fp16 9.22ms，
  残余成本是 GEMM 计算本身，对应 TODO #3（chunk 并行 prefill）。
- **16x16 仍落后 faster3a**（9.22 vs 7.78ms）：faster3a 是真 batch `[16,16]` 并行，
  rwkv_tl 是 256 tokens 单序列顺序递推。要追平需真实 batch 支持（见
  `.agent/architecture.md` "Future: real batch"）。

### 落后原因分析（profiler 实测，2026-08-10）

真 batch 的 16x16 不在分析范围（等未来真 batch 支持）。排除后落后的 case：
**decode 1x1**（0.4B 1.47x、1.5B 2.39x）与 **1.5B 大 T prefill**（T=64/128/8x8，
1.09-1.33x）。逐项 profiler 拆解（torch.profiler, CUDA activity，GPU kernel 时间）：

#### 1. decode (1x1) —— r/k/v GEMV 占 60%+，且链中膨胀 4.8x

`tmix_decode` 单层 = prologue(LN+6-shift) + r/k/v 三个 GEMV + 打包 rank GEMV +
rank-out/gate + L2norm + DPLR + GN + oWt GEMV + x0 残差 ≈ **11 个顺序 kernel**。
三模型 decode GPU 时间占比（r/k/v GEMV 合计）：

| 模型 | r/k/v GEMV | head GEMV | torch elementwise |
|---|---|---|---|
| 0.1B (3.17ms) | r 0.58 + k 1.33 + v 0.27 = **2.18ms (69%)** | 0.30ms | 0.15ms |
| 0.4B (7.84ms) | r 1.56 + k 3.44 + v 0.71 = **5.71ms (73%)** | 0.41ms | 0.33ms |
| 1.5B (17.6ms) | r 3.94 + k 7.16 + v 1.46 = **12.6ms (72%)** | 0.79ms | 0.81ms |

关键证据：
- **GEMV 单 kernel 不慢**：微基准 tilelang `gemv_macro` C=768/1024/2048 = 16.8/19/63us，
  cuBLAS `torch.mv` = 16.4/14.2/44us——两者相当或 tilelang 略快。
- **但 decode 链中每个 k GEMV 膨胀到 55us（0.1B）/71us（0.4B）/149us（1.5B）**，
  是微基准的 2.4-3.8x。
- **faster3a 对照**：0.4B decode 2.63ms，r/k/v 投影用 `linear_orig_row1_exact4_f16`
  专精 kernel，**每个仅 14.8us**（121 calls 共 1.79ms）。我们慢 ~4.8x。

根因：`tmix_decode` 单层 11 个 kernel **顺序执行、无法 overlap**——每个 GEMV 的输入
是前一 kernel 刚写的 global buffer（r 依赖 prologue，k/v 依赖各自 shift），launch 间隙
+ 数据依赖 + 低 occupancy（每 GEMV 只有 24-64 个 32-thread block）叠加。微基准无依赖、
L2 热，测不出这个代价。faster3a 把 r/k/v 投影融进一个 row1 专精 kernel + 每层更少
launch（0.4B 290 kernels/decode vs 我们 ~440）。

次要：decode 末的 `head @ ln_out` 是 cuBLAS GEMV `[65536, C]`（0.4B 413us / 1.5B
792us），faster3a 融合进 HEAD 逻辑避免了单独 launch。

→ 修复方向（TODO #1/#7）：把 r/k/v 三个 GEMV 合并成一个 batched GEMV kernel；
`tmix_decode` 单层 11 kernel 融合到更少；HEAD 专精。decode 单 kernel 已够快，瓶颈是
**融合度**不是 GEMV 本身。

#### 2. 1.5B 大 T prefill（T≥64）—— TMIX 未融合 + DPLR 慢 6.3x

1.5B prefill 的 TMIX 仍走旧逐 op 路径（`demo.rwkv7_tl.time_mix_batch`）：
`fused_rkv_gemm` + 6 个 torch shift lerp + gates + `fused_dplr_T` + `out_mm`。
单层 T=64 拆解：

| 项 | 耗时/层 | 说明 |
|---|---|---|
| `fused_dplr_T` | 296us | faster3a `wkv_fp16_seq_v2` 仅 **47us，慢 6.3x** |
| `fused_rkv_gemm` | 189us | 旧 tilelang；faster3a 用 cuBLAS 大 tile |
| `out_mm` | 48us | |
| torch elementwise（6 shift + gates） | ~90us | Python 逐 op + launch |
| **合计** | **~530us** | ×24 层 ≈ 12.7ms + CMIX |

DPLR 慢因：`fused_dplr_T` grid `(H,N)`=32×64=2048 blocks、每 block 32 threads 串行
整个 T，occupancy 低、无 chunk 并行。faster3a 用 chunk 并行 + cp.async 流水线。

→ 修复方向（TODO #3）：TMIX prefill 融合（`tmix_prefill`）+ chunk 并行 DPLR。1.5B
T=128 落后 1.33x 的差距大部分来自这两项。

#### 3. 16x16 —— 真 batch，不做（等未来）

faster3a 真 batch `[16,16]` 并行，rwkv_tl 是 256 tokens 单序列串行递推。已知差异，
非优化问题，等未来真 batch 支持再比。

### 结论（2026-08-10 更新）

- **prefill T=8/32/64 三模型领先 faster3a 1.6-2.4x**（graph 消除 launch 后 GEMM 不输
  cuBLAS）。**0.4B 1x128 也领先（1.06x）**。
- **decode 1x1 全面回归**：旧基线 2.36ms（0.1B）→ 4.30ms；0.4B/1.5B 落后 faster3a
  1.47x/2.39x。根因是 `tmix_decode` 单层 11 kernel 顺序执行使 r/k/v GEMV 膨胀
  4.8x（非 GEMV 本身慢）。graph decode 4.15ms 还比 eager 3.44ms 慢（State copy-in/out
  36 次小 copy_ + `.item()` 同步）。见上方分析 #1。
- **1.5B 大 T prefill（T≥64）落后**：TMIX 未融合 + DPLR 慢 6.3x。见上方分析 #2。
- 16x16（真 batch）不做对比，等未来。
- 这是 decode/prefill 优化（TODO #1/#3/#7）的直接对比基线。

## fused prefill 接入（9e81fd1）在 3060 上倒退：串行 oWt GEMV 根因（2026-08-12）

commit 9e81fd1 把 prefill 的 TMIX 改为融合 `_tmix_prefill_front/_back`（rkv 投影用
fp16 T.gemm），commit 声称 MX450 上 prefill 快 2.1x 且 T≥32 追平 faster3a。**但在
本机 3060 (sm_86) 上 prefill 全面倒退**（0.1B T=128 5.19→30.3ms，0.4B 14.6→114.8ms，
1.5B T=128 35→386ms；decode 因 v_first 修复略好：0.1B 4.30→3.67ms）。

### 三模型退化数据（tl-fp16，p50 ms，warmup=10 iters=30）

| 模型 | case | 旧 (a8e2ef7) | 新 (9e81fd1) | 变化 |
|---|---|---|---|---|
| 0.1B | 1x1 | 4.30 | 3.67 | -15% |
| 0.1B | 1x32 | 3.46 | 8.87 | **+156%** |
| 0.1B | 1x128 | 5.19 | 30.27 | **+483%** |
| 0.4B | 1x32 | 8.16 | 28.87 | **+254%** |
| 0.4B | 1x128 | 14.64 | 114.79 | **+684%** |
| 1.5B | 1x32 | 16.12 | 101.93 | **+532%** |
| 1.5B | 1x128 | 35.03 | 386.46 | **+1003%** |

T 越大退化越严重（1.5B T=128 慢 10x）。decode 略好（v_first 修复）。

### profiler 定位（0.1B，T=128，torch.profiler GPU 时间）

单层 TMIX = front(672us) + back(1842us)。back 占 73%，其中：

| kernel | 耗时 | 说明 |
|---|---|---|
| `_impl_kernel_2`（oWt 投影） | **1704us** | **逐-token 串行手写 GEMV** |
| `_impl_kernel`（DPLR） | 141us | serial over T，正常 |
| `_impl_kernel_1`（GN） | 89us | grid 仅 H 个 block，欠并行 |

**根因**：`_tmix_prefill_back` 的 oWt 投影写成
`for t in T.serial(LEN): for k in T.serial(C): acc += gy[t,k]*oWt[k,...]`——
双层串行、完全未并行（T=128 × C=768 = 98304 步串行累加），未用 tensor core。
**旧路径 `out_mm` 用 batched `T.gemm` 只要 63us**（微基准实测），慢 **27x**。

GN kernel 同样 `for t in serial(LEN)` 且 grid 只有 H=12 blocks（0.1B），欠并行。

### 为什么 MX450 快、3060 慢

串行 GEMV 在 MX450 (sm_75) 上相对其病态 fp16 cuBLAS 反而可接受（MX450 的 fp16
cuBLAS 小 shape 慢 4-8x，见 git 历史中的 MX450 特调记录），所以 commit 在 MX450 测出 2.1x。
但 3060 (sm_86) 的 tensor core 未利用，串行写法的劣势暴露。

### 修复方向（报告，未改代码）

`_tmix_prefill_back` 的 oWt 投影改用 batched `T.gemm`（`[T,C]@[C,C]`，复用
`kernel/old/gemm.py` 的 `out_mm` 模式，实测 63us vs 1704us）；GN 也改 batched
（grid 按 T 展开而非 serial）。修完 prefill 应回到旧水平（0.1B T=128 ~5ms）。

### 修复结果（commit 3d05ebd + 493e3e6，2026-08-12）

已在 3060 上修复并提交：

| 模型 | case | 9e81fd1 倒退 | 修复后 | 修复倍数 |
|---|---|---|---|---|
| 0.1B | T=128 | 30.3ms | **11.3ms** | 2.7x |
| 0.4B | T=128 | 114.8ms | **31.5ms** | 3.6x |
| 1.5B | T=128 | 386.5ms | **82.2ms** | 4.7x |

两步修复：
1. **3d05ebd**（back）：oWt 投影改 batched `T.gemm`（1704→~63us，27x）；GN 并行化
   （grid (H,)→(LEN,H)）。三模型 T=128 均改善 2.5-2.7x。
2. **493e3e6**（front rank 一阶）：rank 一阶 flat kernel（`LEN*Rmax*4` blocks，1.5B
   时 5.6ms/层）改 4 个打包 `T.gemm` `[LEN,C]@[C,R]`（共 ~0.47ms/层）。1.5B T=128
   再降 2.4x（198.7→82.2ms）。

正确性：fp16 套件 17 passed；greedy `generate` 输出与修复前逐 token 一致。
剩余差距（vs 旧基线 a8e2ef7）：front 的 rank-out flat kernel（1.5B 1.45ms/层，
`LEN*C` blocks）仍是主要成本；打包成 `[LEN,Rsum]@[Rsum,C]` GEMM 可再降 ~4x
（实测 333us vs 1450us），但需激活分离 + 权重转置，留待后续（TODO）。

### 规律

- **小模型 + 小 T：全面赢**（0.1B T≤64，0.4B T=8..64）。graph 消除 launch + 融合
  kernel 在 C 小、T 小时胜出。
- **C 越大 decode 越输**：0.1B T=1 赢（0.81x），0.4B 输 1.39x，1.5B 输 2.06x。
- **所有模型大 T prefill 输**（T≥128 后 1.5-2.0x），差距随 T 增长。

### 原因分析

**① decode（T=1）—— 单行 GEMV 结构差异**
- 我们的 `tmix_decode` 每层 ~9 个顺序 kernel，rkv/oWt 用 `gemv_macro`
  （32 threads/block、lane-per-output、K 标量串行读）。
- faster3a 用 `linear_orig_row1_exact_f16_kernel`（128 threads/block、每 block 算
  OutTile=2 输出、4 warp partial + warp_sum、**K 用 half2 向量化**、2 FMA/线程）。
- 微基准（1.5B C=2048）：gemv_macro 64us vs cuBLAS 43us；decode 链中膨胀到
  94-146us（多 kernel 串行 + global 依赖 + 低 occupancy）。
- faster3a 41.7us/个（120 calls 覆盖所有线性投影）。C 越大差距越大（1.5B 最差）。
- → 修复：decode 单行 GEMV 改 faster3a 风格（128 threads + half2 向量化 + 多
  warp reduce），或融合 r/k/v + oWt 投影。

**② prefill 中 T（T=32..128）—— GEMM 计算量随 C 放大**
- 0.1B/0.4B 赢（融合 + graph），1.5B 输 1.3-1.7x。C=2048 时 front 的
  rank GEMM（4 个）+ rkv GEMM 计算量是 0.1B 的 ~7 倍，且串行 T 的 DPLR 在
  大 C 下 latency 暴露。
- faster3a 用 cuBLAS batched GEMM 处理这些（大 tile + split-K）。

**③ prefill 大 T（T≥256）—— 串行 DPLR latency 主导**
- 即使 fp16 register state（已对齐），串行 over T 的 DPLR 在 T 大时 latency
  主导。faster3a 的 cp.async 双缓冲预取隐藏了内存延迟。
- 0.1B/0.4B/1.5B 大 T 全输 1.5-2.0x。

### 结论

- **小模型（0.1B/0.4B）prefill 已赢 faster3a**，main 瓶颈是大 T 的串行 DPLR。
- **1.5B 全面输**：decode 输在单行 GEMV 结构（①），prefill 输在 GEMM 规模放大（②）。
- 三个可行动优化：① decode 单行 GEMV 重写（faster3a 风格）；② rank/rkv GEMM 合并
  减少 kernel 数；③ DPLR 大 T 用 cp.async/多 block 并行（TODO #3）。

## torch.compile 相关实验

### 结论

- 在 MX450 上，torch.compile 并没有带来收益，甚至明显变慢。
- 主要原因是该硬件的 sm_75 架构不适合 bf16 编译路径，inductor 会退回到更慢的 fallback 路径。
- 该结果不应被解释为 RTX 30 系列或更高架构上的通用结论。

### RTX 3060 (sm_86) 验证

目标卡上重新验证了编译路径，结论：

- **decode (`decode`)**: graph breaks = 0（custom op 包装生效）。但 compiled 与 eager 几乎相同甚至更慢（0.1B: 44-49 vs 43-46 ms/token，speedup ~0.88-1.04x），没有额外收益。
- **prefill (`prefill`)**: 先把 `make_TMIX_batch` 的 `fused_rkv_gemm` / `fused_dplr` 接线到 custom op 后，graph breaks 从 3 降到 0。编译后 0.1B 各 T 均更快：

  | T | eager ms | compiled ms | speedup | 首次编译耗时 |
  |---|---:|---:|---:|---:|
  | 8 | 43.7 | 30.6 | 1.43x | 22.6 s |
  | 16 | 70.4 | 50.8 | 1.39x | 31.4 s |
  | 32 | 128.2 | 102.7 | 1.25x | 60.7 s |
  | 64 | 227.5 | 186.5 | 1.22x | 126.9 s |
  | 128 | 479.1 | 398.2 | 1.20x | 289.5 s |
  | 256 | 841.6 | 759.8 | 1.11x | 702.1 s |

- **决策**: prefill 保持 eager，不启用 `maybe_torch_compile`。原因：DPLR 串行循环按 T unroll，每个不同 prompt 长度都重编译一张新图，编译耗时随 T 快速增长（T=256 约 12 分钟，期间 GPU 空闲），而稳态收益仅 1.11-1.43x。对长上下文 / 动态长度不划算。`make_TMIX_batch` 也回退到直接调 raw kernel（不经过 custom op，避免 dispatch 开销）。
- `_compat.maybe_torch_compile` 的缓存键改为 `f"_{fn.__name__}_impl"`，支持同一实例上多个方法各自编译（本次仅 `decode` 使用）。

### 观察

- `forward` / `prefill` 的图断裂数在实验中为 0，说明 custom op 包装可以避免编译时的图断裂问题。
- decode 路径中，`Tensor.item()` 仍会引入一次同步，因而无法完全消除所有图断裂（`forward` 单 token 分支在 __init__.py:292 处 graph break，graphs=2/breaks=1，但 `forward` 不编译所以无实际影响）。
- 数值一致性：compiled prefill 与 eager 的 max_diff=0.19，argmax 一致。
- 手动 `torch._dynamo.explain(m.forward)` 时，若 `_decode_impl` 尚未预热，`maybe_torch_compile` 包装器会在 dynamo 追踪内递归 `torch.compile`（RecursionError）。运行时首次真实调用会缓存 impl，正常流程不受影响。

### 进一步建议

- 对 decode-only 的 compile 策略可以保留（graph 干净、无额外编译成本），但不把它当作默认性能手段。
- 对 prefill 路径，当前更值得优先做的是 kernel 级别和访存路径的优化，而不是继续依赖 torch.compile。
- 若未来启用编译 prefill，考虑按 (T) 缓存编译图或限定固定长度，避免扫表场景的重复编译。

## benchmark_rwkv7.py 扫描注意事项

- `prefill` 一旦被 `maybe_torch_compile` 包装，benchmark 每个不同 T 的 case 都会触发一次全新编译（0.4B 的 16×16 要 20+ 分钟），GPU 空闲、看起来像死锁。benchmark 现在通过 `_eager_dispatch` 走 eager 路径测实现本身；编译收益单独用脚本测。
- 大规模 benchmark 在显存和内存受限的机器上容易触发 OOM，建议按 case 分开运行。
- 对于长时间扫描，优先使用独立进程和日志文件方式执行，避免单次前台进程被中断。

## decode 全融合单 kernel 的可行性评估（RTX 3060, 0.1B）

背景：曾想用 tilelang 把 decode 的逐层 Python 循环（`for TM, CM in self.layers`）融合成一个动态层数的单 kernel，消除 ~130 次 kernel launch。

测量结论：
- eager decode 13.1 ms/token（wall），纯 GPU 11.1 ms；单次 decode 有 27 次 launch（~130 个小 kernel），主要为 GEMV（~1 ms）、`_fused_rkv_gemm`（12 次）、`_impl` reduce（95 次）、layernorm、elementwise。
- **CUDA-Graph decode（`CUDAGraph` 包装器）已到 1.63 ms/token**，且 profiler 显示 GPU kernel 总执行仅 1.55 ms、launch 间隙仅 ~0.08 ms。即 launch 开销已被 CUDA Graph 几乎完全消除。
- 因此"全融合单 kernel"的理论上限 ≈ 1.55 ms，相对 CUDA-Graph decode 只省 ~0.08 ms，收益极小。真正剩余成本是 ~1.5 ms 的 GEMV 计算本身，而非 launch。

技术验证（tilelang）：
- `T.gemm` 要求 M ≥ 16（MMA tile），decode 是 M=1 的 GEMV，不能直接用；手写 block-per-row + warp_reduce 的 GEMV 正确且比 cuBLAS `mv` 快（11.3 vs 17.4 μs @ C=768）。
- `sync_grid` 需要 cooperative launch：grid=768 blocks × 32 threads 在 RTX 3060 上报 `CUDA_ERROR_COOPERATIVE_LAUNCH_TOO_LARGE`，动态层数大网格不可行。
- `@T.macro` 能复用 tilelang 代码片段（编译期内联，多 kernel 共享），但宏内**不能用 Python 条件分支切换张量索引**（`if batched:` 会被 tilelang 当运行时条件，生成错误代码）。因此 DPLR 的两个 kernel（T=1 输入 `[H,N]`、T>1 输入 `[T,H,N]`）索引布局不同，无法共用同一个宏；统一成 3D 布局需改 `fused_dplr` 公开契约，不值得。结论：DPLR 保持两处独立实现，不抽宏。

方向决策：
- **rwkv-tl 长期目标支持训练**。CUDA Graph 本质 inference-only：捕获前向启动序列、不重建 autograd 图（replay 不记录梯度，固定 buffer 与 autograd 动态建图冲突）。全融合单 kernel 并非本质 inference-only（任何自定义 kernel 都要显式 backward），但整层融合会让训练困难：需手写整层 backward（含串行 DPLR 递推的时间反向）并手工保存各算子的中间张量，远超 per-op custom op 路径的工作量。
- 正确的训练路径是保留 `torch.library.custom_op`（`torch.ops.rwkv_tl.*`），通过 `register_autograd` 定义 backward。
- 结论：decode 的优化应聚焦 CUDA-Graph decode 那 1.5 ms GEMV 计算本身（如 output/FFN/低秩 gates 的 GEMV 优化），而不是全融合层数。不要为"融合"投入，除非能保持 autograd 能力。

## prefill FFN GEMM 融合的可行性评估（RTX 3060, 0.1B, 2026-08-06，二次修正）

背景：想把 prefill 的 CMIX（FFN）两段 GEMM 融合，减少 kernel 数并让 `[T,4C]` 中间量少往返。

### 第一次尝试（错误结论）

全融合单 kernel（up+relu²+down+残差，K-tiling 结构）实测 ~20x 慢于 eager。当时归因为
"tilelang T.gemm 打不过 cuBLAS"，结论是 FFN GEMM 融合死路。**该归因是错的**——真正原因是
**1D grid**：只按行切 block，整个 3072 宽 hidden 在一个 block 里串行算，GPU 严重欠并行。

### 二次测量（修正）

改用 **2D grid**（行 × 输出列都切块），tile 配置 BM32/BN128/BK32/threads128/stages2：

| 方案 | N=16 | N=32 | N=64 | N=128 | N=256 |
|---|---|---|---|---|---|
| tilelang 纯 GEMM `x@kWt` | 0.0218 | 0.0229 | 0.0336 | 0.0382 | 0.0737 |
| cuBLAS 纯 GEMM `x@kWt` | 0.0209 | 0.0218 | 0.0227 | 0.0358 | 0.0628 |
| tilelang up+relu² 融合 | 0.0183 | 0.0220 | 0.0223 | 0.0362 | 0.0682 |
| eager `relu(x@kWt).square()` | 0.0431 | 0.0358 | 0.0330 | 0.0867 | 0.0758 |
| tilelang up+down 两 kernel | 0.0646 | 0.0645 | 0.0704 | 0.0854 | 0.1378 |
| eager 全 CMIX（5 kernel） | 0.0685 | 0.0684 | 0.0646 | 0.0760 | 0.1549 |

（耗时 ms；3060 噪声较大，单次会话相对比较可靠）

结论：

1. **tilelang `T.gemm` 本身不慢**：2D grid + 合适 tile 下纯 GEMM 与 cuBLAS 持平。
   `gemm.cc` 的指令选择（sm_86 → m16n8k16 MMA）不是瓶颈。之前"3x 慢于 cuBLAS"是
   1D grid / 差配置的假象（仓库现成 `fused_rkv_gemm` 也是配置问题，非 tilelang 缺陷）。
2. **真正能赢的是 epilogue 融合**：把 relu²/add 融进 GEMM 的寄存器 epilogue，省掉
   relu/square/add 单独 kernel 对 `[T,4C]` 的读+写。up+relu² 融合在 N=16 快 2.4x、
   N=128 快 2.4x（相对 eager relu+square）；up+down 两个 2D kernel 整体约 parity~1.06x。
3. **全融合单 kernel 仍不可行**：hidden `[BM,4C]` 必须留片上 → 强制 1D grid（欠并行）
   + 每 block 重读整张权重。保留为参考（`kernel/cmix.py` 的 `fused_cmix_full_reference`）。

方向：`kernel/cmix.py` 的 `fused_up_relu2` / `fused_down_add`（2D grid + epilogue）
作为 FFN 融合的可用版本；端到端收益待接入 prefill 后测量。


## cmix_prefill（整链融合 CMIX）基准（RTX 3060, 0.1B C=768, 2026-08-08）

背景：`kernel/cmix.py` 的 `cmix_prefill`（曾名 `fused_multi_cmix`，cc09d44 重命名）
把 CMIX 整条链融进一个 prim_func——
LN_pre → token-shift lerp（内部读 x[n-1]）→ state 更新 → up GEMM → relu² → down GEMM → 残差，
5 个 `with T.Kernel`（编译成 5 个独立 kernel、1 次 host 调用顺序 launch）。
对比 eager CMIX（python 中介：aten LN + cat + lerp + `state.copy_` + 2×cuBLAS + relu² + add）。

### 墙钟对比（T = LEN，LEN_block=32，warmup=50，iters=300）

| T | cmix_prefill | eager CMIX | 加速比 |
|---|---|---|---|
| 32 | 0.072-0.125 ms | 0.146-0.175 ms | 1.2-2.0x |
| 64 | 0.078-0.081 ms | 0.150-0.175 ms | 1.9-2.2x |
| 128 | 0.090-0.161 ms | 0.126-0.166 ms | 1.03-1.4x |
| 256 | 0.149-0.289 ms | 0.158-0.250 ms | 0.87-1.06x |

（两次独立运行取区间；3060 噪声大，T=32/256 区间较宽，T=64/128 结论稳定）

正确性：max_abs 误差 0.125（输出量级 max|ref|≈102，相对 0.12%，fp16 全链路累积，正常）。
约束：`LEN % LEN_block == 0`（当前 LEN_block=32）。

### kernel 剖析（T=128）

| kernel | 耗时 | 占比 |
|---|---|---|
| down GEMM（`_impl_kernel_4`） | 0.046 ms | ~48% |
| up GEMM（`_impl_kernel_3`） | 0.037 ms | ~39% |
| LN/lerp/copy 前段（3 个 kernel） | ~0.007 ms | ~7% |

### recompute 开/关对比（cmix_prologue_prefill，2026-08-10 本机实测）

`cmix_prologue_prefill` 的 token-shift 源有两种策略（`recompute` 参数）：
- **recompute=True（默认）**：2 个 kernel。每个 block 本地重算 `LN_pre(x0[n-1])`
  （只读不可变 `x0`，无跨 block 依赖），LN+lerp 融进 1 个 kernel；代价是 LN 计算量
  翻倍，省 1 次 launch。cc09d44 提交信息称 MX450 (sm_75) 上快 14-32%。
- **recompute=False**：3 个 kernel。kernel 1 全量 LN 写 `x_ln`，kernel 2 读
  `x_ln[n-1]` 做 lerp，kernel 3 拷回 `prev_x`。

**本机 RTX 3060 (sm_86) 实测**（C=768, fp16，5 次独立 run 取中位数，整链 `cmix_prefill`）：

| LEN | recompute=True | recompute=False | 加速比 | 胜者 |
|---|---:|---:|---:|---|
| 32 | 0.142 ms | 0.147 ms | 1.04x | True |
| 64 | 0.140 ms | 0.148 ms | 1.06x | True |
| 128 | 0.142 ms | 0.222 ms | 1.57x | True |
| 256 | 0.155 ms | 0.166 ms | 1.08x | True |
| 512 | 0.252 ms | 0.251 ms | 1.00x | 持平 |

- **recompute=True（默认）在 3060 上全面胜出或持平**（T=128 达 1.57x），
  与 MX450 上的结论一致；T=512 打平（大 T 时 GEMM 占绝对主导，prologue 差异被摊薄）。
- 正确性：两种实现 max_abs 0.002（fp16 ULP 级），`prev_x` 完全一致——数值等价。
- 结论：保持默认 `recompute=True` 正确，无需按硬件分支。

### 结论

- **小-中 T 快 1.4-2.2x**：主要来自减少 kernel 数（5 个 1 次调用 vs eager ~9-10 个 python 算子）
  和去掉 `cat`/shift 的 `[T,C]` 中间量往返；GEMM 本身是 tilelang，与 cuBLAS 持平。
- **大 T 趋平（~1.06x）**：T 大后 GEMM 计算占绝对主导，前段融合收益被摊薄。
- **优化方向**：时间 ~87% 在 up/down GEMM，进一步收益要靠 GEMM 本身
  （但 sm_86 上 tilelang GEMM 仅与 cuBLAS 持平，见上文 FFN 融合评估），前段（LN/lerp）占比很小。
- 注意：模型 prefill 走 CUDA-Graph（消除 launch 开销）时，fused vs eager 的差距预计缩小，
  但 fused 省掉的 `cat`/shift 中间量往返在 graph 模式下仍在；是否值得在 graph 模式用需另测。

## decode 低秩 gate 融合基准（fused_rank_gemv + fused_gates，2026-08-08）

两个新 kernel（分支 commit 66d03ac，TODO #8）在 decode 路径替换：
- `fused_rank_gemv`：打包 `[v1t; w1t; a1t; g1t] @ [xv; xw; xa; xg]` 单 kernel（原 4 个 cuBLAS fp16 GEMV）。
- `fused_gates`：rank-out 第二步 + tanh/sigmoid 激活 + v/w/a gate 数学单 kernel（原 4 rank matmul + 2 激活 + 3 gate op）。

本机 3060 实测（C=768, Rv/Rw/Ra/Rg=32/64/64/128，warmup=100, iters=500）：

| 路径 | 耗时 |
|---|---|
| eager（8 个算子） | 0.253 ms |
| fused（2 kernel） | 0.050 ms |
| 加速比 | **5.05x** |

- 与 TODO 记录（MX450 上 ~5.3x）一致；本机 3060 重复验证。
- 这是 decode 路径除 CUDA-Graph 之外的真实 kernel 级收益（替换 4 个病态 cuBLAS fp16
  GEMV + 6 个离散算子为 2 个手写 kernel）。已接入 eager 和 custom-op 两条路径。
