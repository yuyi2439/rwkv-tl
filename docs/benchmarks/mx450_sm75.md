# MX450 (sm_75) benchmark 结论

本文件记录 `tl-mx450` 特调在 Turing sm_75（MX450）上的性能结论与原因分析。
可复现数据见 [script/benchmark_rwkv7.md](../../script/benchmark_rwkv7.md)。

## tl-mx450 特调 vs 适配 sm75 的 faster3a_2607

对比对象：本项目 `tl-mx450`（fp32 prefill GEMM + T≤16 tilelang fp16 rkv + CUDA Graph decode）
与 [yuyi2439/Albatross](https://github.com/yuyi2439/Albatross) `support/sm75` 分支适配的
faster3a_2607。0.1B / MX450，实测数据见主报告，以下为 kernel 级剖析结论（2026-08-04）。

### T=1 decode：mx450 赢在确定性，不是原始算力

- faster3a 的 `linear_ori` GEMV 仅 **5.6ms GPU**，min wall 7.0ms——计算比 mx450（8.1ms）更快。
- 但 faster3a 的 wall 波动 7~26ms（Python/extension dispatch + GPU jitter），p50 8.6ms。
- mx450 CUDA Graph：wall≈GPU=8.3ms ± 0.8，完全确定（replay 消除 launch 间隙）。
- → benchmark 里 mx450"赢"是稳定性的胜利；faster3a 的理论下限更低。

### T=2/4/8 小 prefill：faster3a 赢，launch 开销主导

- mx450 eager prefill 37-40 个 kernel：T=4 GPU 仅 12.1ms 但 **wall ~25ms（~2x 差距）**——
  小 fp32 GEMM 每个 ~µs，被 37 次 launch + 逐层 Python dispatch 淹没。
- faster3a 28 个 kernel、融合路径更紧，wall≈GPU（8.9 vs 9.5ms）。
- 小 prefill 是 launch-bound：faster3a 的 kernel 少、dispatch 开销小。

### T≥16 prefill：mx450 赢，根本原因是 fp16-vs-fp32 GEMM

- faster3a 在 T=32 用 `volta_fp16_s884gemm_fp16` fp16 tensor-core GEMM **39ms/42.6ms GPU**——
  正是 Turing fp16 cuBLAS 病态（与 c2c4283 迁移 fp16 后 tl prefill 变慢同因）。
- mx450 用 fp32 GEMM（20ms @ T=32）绕开病态路径。
- T 变大后 launch 摊薄，GEMM 效率决定胜负 → mx450 1.3-1.4x。

### 补充发现：非连续权重是隐藏的大坑（2026-08-04）

- kernel 级剖析发现 prefill 的瓶颈其实是 **CMIX（FFN）**，不是 TMIX 门链：
  单层 CMIX 3.68ms，其中 2 个 `volta_sgemm_64x64_tn`（`[T,768]@[768,3072]` +
  `[T,3072]@[3072,768]`，FFN 4x 扩张）占 3.33ms。
- 根因：`ffn.kWt.T` / `vWt.T` 是**非连续转置视图**（stride `(1,N)`），
  cuBLAS 对非连续操作数慢 ~2.7x（实测 1.52 vs 0.55ms @ T=128）。
- 修复：所有 GEMM 权重 `.T` 后加 `.contiguous()`。**MX450 prefill T=128 从 70.6 → 43.4ms
  （-39%）**，现在比 faster3a（88.6ms）快 2.04x。tl-fp16 不变（fp16 cuBLAS 病态主导）。

### 补充发现：小 T prefill 是 launch-bound，用 CUDA Graph 消除（2026-08-04）

- 小 T（2..8）prefill 的 **launch 数恒定 ~2175**（与 T 无关，每层 op 序列固定），
  T=4 GPU 仅 12ms 但 wall ~33ms——~20ms 是 2175 次 launch 的 Python + 调度开销。
- 解法：`CUDAGraph` 包装器把整段 prefill 按**精确 T** 捕获成
  CUDA Graph 回放（DPLR 递推逐 token 推进状态，不能 pad），copy-in/out 保持模型无状态。
- 结果：T=4 33 → 11.7ms，T=8 30 → 13.0ms，T=32 33 → 15.8ms。**MX450 现在每个 T 都
  赢或打平适配 sm75 的 faster3a**（见 [script/benchmark_rwkv7.md](../../script/benchmark_rwkv7.md)）。
- 前提：batch 闭包 `state["x"]` 必须 in-place `copy_`（不能 rebind），固定 buffer 才能捕获。
- T>64 保持 eager（launch 开销已摊薄，graph 内存随 T 增长）。

### 核心结论

- 所谓"适配 sm75 的 faster3a" 仍然跑 fp16 tensor-core GEMM，撞上 Turing 病态；
  **MX450 的 fp32 选择才是更到位的 sm75 适配**。
- T=1 是 CUDA Graph 消除 launch 的确定性优势（stateless 设计：任意 `State` 可用）。
- **非连续 cuBLAS 操作数在 Turing 上慢 ~2.7x，GEMM 权重 `.T` 后必须 `.contiguous()`**——
  这比写融合 kernel 更简单更有效。

## 其它 MX450 关键结论

- fp16 cuBLAS 在 Turing 上病态：rkv / 输出投影 / 低秩 GEMM 全部 4-6x 慢于 fp32，
  因此 prefill 的 fp16 GEMM 走 T 特化 tilelang fp16 m16n8k8 kernel（见
  [AGENTS.md](../../AGENTS.md) Known issues）。
- **CUDA Graph decode 的 stateless 设计**：模型不持有 state；`decode` 把调用方 `State`
  拷入 graph 固定 shadow → 回放 → 拷回，任意 `State` 可用。

## 补充发现：rkv 三 GEMV 融合单 kernel（2026-08-11）

`tmix_decode` 的 r/k/v 三个独立 GEMV 合并为一个 batched GEMV（2D grid，bz 选投影，
权重用 stacked `rkvWt [3,C,C]`，输出 stacked `rkv [3,C]`）；first-step rank GEMV
改 2D grid `(max_rank, 4)`（bz 即 gate，每 gate 独立宏，去掉原 `j < Rv+Rw`
段偏移判断）。

0.4B / MX450 fp16，单会话同跑（warmup=5, iters=20，`--targets faster3a_2607` 与
`tl-fp16` 各独立进程，热降频使绝对延迟偏大，同会话相对比较可靠）：

| Case | faster3a_2607 | tl-fp16 (融合后) |
|---|---:|---:|
| 1x1 decode | 26.61ms | **21.48ms (1.24x)** |
| 1x8 decode | 65.02ms | **56.15ms (1.16x)** |

- 融合前旧路径 0.4B 1x1 慢于 faster3a（neo 基线 9.85 vs 6.71ms on 3060）；本次 MX450
  上融合后 decode 反超 faster3a ~1.2x。
- 正确性：`test_neo_tmix` 0.1B/0.4B 全过，rnn/out max_abs 同原路径。
